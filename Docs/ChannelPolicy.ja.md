# チャンネル方針: 包含基準と優先度ルール

この文書は、次の 2 点を厳密かつ定量的に定義します。

- どの YouTube チャンネルをデータセットに含めるか(基準 C1〜C6)
- Data API の作業をどの順で行うか(レーンと優先度ルール)

`Config/ChannelPolicy.yaml`、`Config/ApiQuota.yaml`、`Src/GameChatCollector/Selection/`、`Src/GameChatCollector/Operations/` は、この文書を仕様として実装されています。

- 方針バージョン: **1.0.0**(最初のコホートの基準日: 2026-11-24)
- 英語版(正): [ChannelPolicy.md](ChannelPolicy.md)
- システム設計での概要: [SystemDesign.ja.md](SystemDesign.ja.md) の 4.2 節と 4.3 節
- 選択の根拠となる文献: [ResearchNotes/20261124_ChannelSelectionCriteria.md](../ResearchNotes/20261124_ChannelSelectionCriteria.md)

## 1. 原則

1. **全候補に同じ規則を適用する。** 候補をどうやって見つけたかで、含めるかどうかを決めません。全ての候補を同じ手順で測定し、同じ閾値で判定します。
2. **バージョンを管理する。** 閾値、観測期間、キーワード、探索枠のパラメータのどれを変えても、新しい `policy_version` になります。データセットの各バージョンは、ちょうど 1 つの `(policy_version, reference_date)` のコホートを使います。
3. **優先度に人気を使わない。** 人気(C4)は包含の閾値には使えますが、作業の順番には使いません。こうしておけば、途中で止まっても大きいチャンネルに偏りません。
4. **全てを記録する。** 不合格の候補も含め、全候補の測定値と結果を保存します。母集団を記述でき、後から閾値を変えた分析(感度分析)もできます。

## 2. 定義

特に断りのない限り、時刻は UTC です。

| 用語                       | 定義                                                                                                                                                                                                                                                                                                                                               |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 基準日 `R`                 | コホートを固定する日。観測期間は `R` の 0:00 UTC で終わります。                                                                                                                                                                                                                                                                                    |
| 観測期間 `W`               | `[R − 180日, R)`(`window_days: 180`)                                                                                                                                                                                                                                                                                                               |
| ライブ配信                 | 公開動画のうち、次を全て満たすもの。`liveStreamingDetails` に `actualStartTime` と `actualEndTime` の両方がある。`actualStartTime ∈ W`。実際の長さ(`actualEndTime − actualStartTime`)が **15 分以上**(`min_live_duration_minutes`)。長さの条件で、テスト配信と大半のプレミア公開を除外します(プレミア公開にも `liveStreamingDetails` が付くため)。 |
| ゲーム配信                 | ライブ配信のうち、`snippet.categoryId ∈ {20}`(ゲーム、`game_category_ids`)のもの。YouTube はゲームカードをゲームカテゴリでしか表示しないので、ゲームカード付きの配信は必ず数えられます。                                                                                                                                                           |
| かな入りタイトル           | ひらがな(U+3041〜U+3096)またはカタカナ(U+30A1〜U+30FA)を 1 文字以上含むタイトル。中黒 `・` と長音符 `ー` は、日本語以外の文にも現れるので対象外です。                                                                                                                                                                                              |
| アップロードの読み込み範囲 | アップロード再生リスト(`UC…` から導出した `UU…`)を新しい順に読みます。`W` の開始日から 14 日前(`playlist_buffer_days`)より古い項目が出たら止めます。20 ページ(1,000 件、`max_playlist_pages`)に達した場合も止めます。14 日の余裕を取るのは、再生リスト上の日付が配信の予約時点の日付で、実際の開始より数日早いことがあるためです。                 |

## 3. 候補の枠組み

### 3.1 検索による枠組み(`search`)

候補の大半は、次の固定パラメータで呼ぶ `search.list` から得ます: `type=video`、`eventType=completed`、`videoCategoryId=20`、`regionCode=JP`、`relevanceLanguage=ja`、`order=date`、`maxResults=50`。

**検索点。** 検索点 `i`(i = 0, 1, 2, …)は、`[T_i − 6時間, T_i)`(`lookback_hours`)を検索語 `q_i` で検索します。

- `T_i = R − F + ⌊vdc(i+1)·F⌋ 日 + ((7·i) mod 24) 時間`
  - `F = 28` 日(`frame_days`)
  - `vdc` は 2 進の van der Corput 列(1/2, 1/4, 3/4, 1/8, …)
- `q_i = terms[i mod 4]`、`terms = ["", "配信", "実況", "ゲーム"]`(`""` はキーワードなし)

この形にした理由:

- **期間を 180 日ではなく 28 日にした。** 動画は公開後 20〜60 日で検索に出なくなります(Rieder, Padilla & Coromina 2025)。直近だけを検索すれば、枠が安定します。その代わり、`R` の約 4 週間より前に配信をやめたチャンネルは、検索では見つかりません。
- **日付に van der Corput 列を使い、時刻を 7 時間刻みにした。** この列は、先頭から何個取っても日付が均等に散らばります。7 と 24 は互いに素なので、時刻は 24 通り全てを巡回します。どの検索点で実行を止めても、枠全体を均等に覆えています。
- **検索語を順に入れ替える。** 時間で区切るだけでは、検索結果の不安定さは直りません(Efstratiou 2025)。検索語の入れ替えは、時間とは独立したもう 1 つの軸になります。
- **`order=date` を使う。** `T_i` 直前に公開された 50 本が返るので、各検索点はその時点のスナップショットになります。チャンネルが見つかる確率は、ゲームカテゴリでの配信頻度に比例します。これは C2 が求める条件と一致しますが、偏りとして記録しておきます。

各検索点の `pageInfo.totalResults` と件数は、生の応答と一緒に `search_points` に保存します。

### 3.2 その他の探索元

- `csv:<label>`: `Config/ChannelCandidates.csv`(`channel_id,source_label,note`)に載せた、事務所の名簿などのキュレーションした一覧。1.0.0 のコホートでは使っていません。
- コラボによるスノーボール(採用済みチャンネルの概要欄で言及されたチャンネル)は、計画中で未実装です。

全ての発見は、探索元と一緒に `candidate_discoveries` に保存します。これで、枠組みの探索元別の構成を報告できます。

## 4. 包含基準

6 つの基準が全て `PASS` のチャンネルだけがコホートに入ります。

| ID  | 基準                 | 測定値                                                                               | 閾値(1.0.0)                                        | 変わりにくいか |
| --- | -------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------- | -------------- |
| C1  | 日本語               | `W` 内のライブ配信のうち、かな入りタイトルの割合                                     | **0.80 以上**                                      | はい           |
| C2  | ゲーム配信の活動量   | `W` 内のゲーム配信の本数                                                             | **8 本以上**(平均 22.5 日に 1 本)                  | いいえ         |
| C3  | ゲーム配信の割合     | `W` 内のライブ配信のうち、ゲーム配信の割合                                           | **0.30 以上**                                      | いいえ         |
| C4  | 規模                 | 評価日に `channels.list` で取得した `subscriberCount`。非公開なら不合格              | **10,000 以上**                                    | いいえ         |
| C5  | チャットの取得可能性 | C5 標本のうち、チャットリプレイがあるものの割合                                      | **0.50 以上**                                      | いいえ         |
| C6  | チャンネル種別       | 切り抜き・転載・企業・パブリッシャー・チームのチャンネルでない。`madeForKids` でない | 必須([チェックリスト](ChannelTypeChecklist.ja.md)) | はい           |

値が定義できない場合は不合格です。ライブ配信が 1 本もなければ、C1 と C3 は不合格になります。

**C5 の標本。** ゲーム配信のうち `sha256(video_id + hash_salt)` が小さい順に `k = min(5, ゲーム配信の本数)` 本を選びます。最新の配信ではなく、再現可能な疑似乱数の標本です。チャットリプレイの有無は視聴ページで判定します。`ytInitialData.contents.twoColumnWatchNextResults.conversationBar.liveChatRenderer` があればリプレイありです。同じページから `game_card_share` も取りますが、これは参考値として記録するだけです。

**C6 の自動フラグ。** 判定に使うのはチャンネル名とハンドルだけです。概要欄には「切り抜き」や「official」が頻繁に現れるため使いません。

- `madeForKids` なら `FAIL`
- `clip_keywords` または `official_keywords` の語を含むなら、人の判定が `Config/ChannelTypeReviews.csv` に記録されるまで `PENDING`
- それ以外なら `PASS`

### 4.1 閾値の根拠

- **C1(0.80)。** かなは日本語に固有で、漢字は中国語と共有されます。タイトル 1 本は短すぎて、統計的な言語判定は安定しません(Jauhiainen et al. 2019)。全タイトルに占める割合で判定すれば、かなを含まないタイトルがときどきある(例: `【APEX】rank`)チャンネルも通せます。実測すると、候補の値はほぼ 1 付近とほぼ 0 付近の二つの山に分かれました。そのため、結果は閾値の厳密な値にほとんど左右されません(8 節)。
- **C2(180 日で 8 本)。** 前例は見つかりませんでした。チャンネル単位の分析に十分な配信本数を確保できる、最小限の定期性の条件です(約 3 週間に 1 本)。実測では、C2 で落ちるチャンネルはごく少数でした(8 節)。
- **C3(0.30)と C4(10,000)。** YouTube での最も近い前例である Ledwich & Zaitsev(2019)にならいました。この研究は「登録者 1 万人超、かつコンテンツの 30% 超が対象分野」で選んでいます。YouNiverse(Ribeiro & West 2021)も登録者 1 万人を使っています。1 万人は YouTube パートナープログラムの入口(500 人 / 1,000 人)の 10〜20 倍で、収益化の基準ではなく、コミュニティが定着している目安です。規模によってチャットの性質は変わります(Nakandala et al. 2017)。C4 はコホートを最も大きく変える閾値なので、感度を報告し、規模帯のフィルタも使えるようにしています。
- **C5(0.50)。** データセットにはチャットリプレイが必要です。大半の配信でリプレイを無効にしているチャンネルは、収集の手間がかかるのにデータが得られません。

### 4.2 評価の手順と状態

高価な測定は合格の見込みがある候補にだけ使うよう、評価は段階的に行います。各候補が使う Data API の unit は次の通りです。

1. `channels.list`(1 回 50 件ずつ、1 候補あたり約 0.02 unit)。次のどれかに当てはまれば、ここで止めて段階を `SCREENED` にします。

   - C6 がすでに不合格(`madeForKids`)
   - チャンネル名、チャンネルの概要欄、発見した動画タイトルのどれにもかながない(C1 の不合格として記録)
   - 登録者数が非公開か、**測定の下限 5,000 人**未満(C4 の不合格として記録)

   下限を C4 閾値の半分にしてあるので、感度分析は 5,000 人まで下げられます。

2. アップロード再生リストと `videos.list`(それぞれアップロード 50 件ごとに約 1 unit)。段階は `MEASURED` になり、C1〜C4 と C6 を判定します。
3. C5 標本の視聴ページ(Data API のクォータは使わない。毎秒 1 リクエスト以下で、ランダムな間隔を足す)。C5 を判定します。

状態の決め方:

- いずれかが `FAIL` → `FAILED`
- そうでなく、いずれかが `PENDING` → `PENDING`
- それ以外 → `PASSED`
- チャンネルが存在しなくなっていれば `NOT_FOUND`

**コホート。** コホートは状態が `PASSED` のチャンネルです。C5 と、フラグが立った C6 が解決するまでは、`Cohort.csv` に `PASSED` と `PENDING` の両方を、未解決の基準名を添えて載せます。

## 5. Data API のレーン

Data API のクォータは 1 日 10,000 unit で、日付は太平洋時間で数えます(0:00 PT にリセット。日本時間では冬は 17:00、夏は 16:00)。`QuotaBudget` は全ての呼び出しを、送信する**前に**レーンへ計上します。レーンの残り予算に収まらない呼び出しは拒否します。

| レーン          | `steady` の配分(unit) | `bootstrap` の配分(unit) | 作業                                                                 |
| --------------- | --------------------- | ------------------------ | -------------------------------------------------------------------- |
| L1 運用         | 30%(3,000)            | 5%(500)                  | コホートのチャンネルの新着動画、ライブ状態の確認、配信後の最終再取得 |
| L2 バックフィル | 40%(4,000)            | 0%(0)                    | コホートのチャンネルの過去配信                                       |
| L3 適格性評価   | 20%(2,000)            | 60%(6,000)               | 候補の測定(4.2 節)                                                   |
| L4 探索         | 5%(500)               | 30%(3,000)               | `search.list` の検索点(1 回 100 unit)                                |
| 予備            | 5%(500)               | 5%(500)                  | 自動では使わない                                                     |

- `bootstrap` は、L1 と L2 の作業がまだない、最初のコホートを作る間だけ使います。通常の運用は `steady` です。
- **配分の開放。** リセットの 4 時間前(`release_hours_before_reset`)から、未使用の配分をまとめて共有します。どのレーンも `9,500 − 当日の消費量` まで使えるようになり、L1 → L4 の順に処理します。
- **クォータの枯渇。** API が `quotaExceeded` を返したら、次のリセットまで API を使う全てのレーンを止めます。Data API を使わない作業は続けます。

## 6. 優先度ルール(各レーン内)

各ルールは並べ替えのキーで、キーが小さいものから実行します。`h(x) = sha256(x + hash_salt)` は、同順位を決める再現可能な疑似乱数です。どのキーにも、登録者数や再生数は含めません。

| レーン | 並べ替えキー                                                                                                                                                                                                                        | 実行できる条件                                                                                                                                   |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| L1     | `(tier, reference_time, h(video_id))`。tier 0: 配信中、または 15 分以内に開始予定(`imminent_minutes`)。tier 1: `actualEndTime` から 2 時間後(`grace_hours`)以降の最終メタデータ再取得。tier 2: 新しく見つけた動画(見つけた時刻の順) | tier 0 は開始の 15 分前から。tier 1 は猶予時間が過ぎてから                                                                                       |
| L2     | `(k, collected_game_hours, h(channel_id))`。スライス `k` は `[now − 30(k+1)日, now − 30k日)`(`backfill_slice_days`)                                                                                                                 | 次のスライスが、コホート全体で最も手前の未完了スライスと一致するチャンネルだけ。スライス _k_ は、全チャンネルがスライス *k*−1 を終えてから始める |
| L3     | `(tier, r, source)`。tier 0: 次のバージョンに向けたコホートのチャンネルの再評価。tier 1: 新しい候補。tier 2: 再挑戦。`r` は同じ tier と最初の探索元の中での `h(channel_id)` の順位で、探索元が順番に回る(ラウンドロビン)            | 再挑戦は待機期間の後だけ。変わりにくい基準(C1、C6)で落ちたら **180 日**、それ以外は **60 日**                                                    |
| L4     | `(times_searched, i)`                                                                                                                                                                                                               | まだ検索していない検索点を、列の順に先に処理する                                                                                                 |

この結果、次のことが保証されます。

- クォータが尽きた時点で、L2 は全コホートチャンネルをほぼ同じ日付まで遡っています。
- L3 は、探索元の大きさにかかわらず、各探索元に同じ割合の評価を割り当てます。
- L4 は、日付、時刻、検索語にわたって枠組みを均等に広げます。

## 7. 出力

`collector channels report` は `Cohorts/Policy<version>_<YYYYMMDD>/` に次のファイルを書き出します。

| ファイル                 | 内容                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------- |
| `ChannelEligibility.csv` | 評価した全候補。状態、段階、不合格・保留の基準、測定値、C6 のフラグ、探索元                     |
| `Cohort.csv`             | 状態が `PASSED` または `PENDING` の行                                                           |
| `Summary.md`             | 段階・状態・探索元ごとの件数、基準ごとの不合格数、各測定値の分位点、閾値を 1 つずつ変えた感度表 |

CSV は BOM 付きの UTF-8 なので、Windows の Excel でもそのまま開けます。全ての測定値(`metrics_json`)と API の生の応答は `Data/`(git 管理外)に残ります。

## 8. 最初のコホート(2026-11-24)

詳しい数値は [Cohorts/Policy1.0.0_20261124/Summary.md](../Cohorts/Policy1.0.0_20261124/Summary.md) を参照してください。主な結果は 8.1 節にまとめます。

### 8.1 結果

実行内容: `bootstrap` プロファイルで、検索点 30 個(3,000 unit)を使い、全候補を評価しました(3,589 unit)。1 候補あたり平均約 2.8 unit、測定まで進んだ候補では約 9.6 unit でした。

- **枠組み。** 30 個の検索点から 1,426 本の動画が得られ、**重複を除いて 1,274 チャンネル**になりました。
  - 904 件は一次判定で止まりました。内訳は、登録者 5,000 人未満または非公開が 832 件、どこにもかながないものが 93 件、`madeForKids` が 1 件です。
  - 残る **370 件を測定**しました。
- **結果。** **253 チャンネルが C1〜C4 と C6 を満たしました。** これらは C5 が未測定なだけで、状態は `PENDING` です。このうち 11 件は、C6 の人手判定も待っています。
- **コホートの規模を決めているのは C4 です。**
  - 閾値を変えたときの件数: 5,000 → 339、1 万 → 253、2 万 → 189、5 万 → 132、10 万 → 94。
  - 登録者数の分布は、対数で見るとほぼ一様です。
  - 規模に左右される分析では、登録者数の帯で層別するべきです(Nakandala et al. 2017)。
- **C1、C2、C3 は閾値を変えても結果がほとんど動きません。**
  - C1 は値が二つの山に分かれるので、閾値を 0.5〜0.9 のどこにしてもコホートの変化は 3 件以内です(1.0 にすると 210 件に減ります)。
  - C2 は 4〜16 の範囲で変化が 10 件以内です。
  - C3 は 0.1〜0.3 の範囲で変化が 5 件です。
  - 検索の枠組みがゲームカテゴリの配信を抽出しているためで、これらの基準が効くのは主に他の探索元からの候補です。
- **測定した活動量。** 測定した候補の中央値は、180 日あたりライブ配信 108 本、ゲーム配信 95 本、ゲーム配信時間 298 時間でした。配信を単位に抽出する枠組みなので、配信頻度の高い配信者が中心になるのは想定通りです。

### 8.2 最初のリストで見つかった問題

- **C6 のキーワードフラグは、メディア企業を見逃し、個人には過剰に反応します。**
  - 見逃しの例: `ファミ通ゲーム実況ch`(メディア企業)にフラグが立ちません。
  - 過剰な例: `狩野英孝【公式チャンネル】`(個人)が「公式」でフラグになります。
  - 1.1.0 での対処として、次の 2 案があります。
    - フラグの有無にかかわらず、コホートの全チャンネルをチェックリストで確認する(約 250 件)
    - キーワードの一覧を増やす
  - キーワードの一覧は完全にはできないので、全件確認を推奨します。
- **「ゲーム」の範囲。** ゲームカテゴリには、現実のプライズ・クレーンゲームや、パチンコ・パチスロの配信も含まれます。これらをゲームに含めるかは範囲の決定なので、次の方針バージョンで決めます。

## 9. 既知の制約

- **検索による枠組み。** ゲームカテゴリで頻繁に配信し、検索の順位で上に来るチャンネルが見つかりやすくなります。母集団をどれだけ網羅しているかは分かりません。CSV の名簿を探索元に加えれば、捕獲・再捕獲法で網羅率を推定できます。
- **カテゴリをゲームの判定に使うこと。** 別カテゴリで行ったゲーム配信は数えられず、ゲームカテゴリで行った雑談は数えられます。この食い違いの程度は、C5 標本の `game_card_share` で測ります。
- **15 分を超えるプレミア公開**は、ライブ配信として数えられます。
- **登録者数**は、API が有効数字 3 桁に丸めています。
- **C5 には視聴ページが必要です。** YouTube はクラウドの IP アドレスにボット確認を返すので、`check-chat` は視聴ページが読み込めるネットワーク(大学や自宅の回線など)で実行する必要があります。
